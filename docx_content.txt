ATS FINAL BOSS
Planned Changes for the 10/10 Version
A practical upgrade plan focused on correctness, stronger experiments, security, and professionalism
Project
ATS Final Boss — Adversarial Resume Screening Defense
Current approach
Keep the existing A/B/C detector architecture and improve it
Main objective
Move from a strong prototype to a reliable, defensible capstone
Guiding principle
Improve the existing system; do not rebuild it unnecessarily
1. Overall Goal
The goal is not to rebuild ATS Final Boss from scratch. The project already has a strong central idea: detect manipulated resumes before they reach an ATS or an LLM-based screener, using multiple signals and then combine those signals into one final decision.
The upgrade strategy is:
Keep the good architecture, fix the weaknesses, strengthen the experiments, and make the results trustworthy.
2. What Will Stay the Same
The main architecture and the project's identity will remain:
Resume
   ↓
Module A ─┐
Module B ─┼──> Meta Classifier ──> Final Result
Module C ─┘
                    ↓
              Explanation
                    ↓
                 Web App
Module A — Keyword Analysis: detects unusual repetition and keyword stuffing.
Module B — PDF Analysis: detects suspicious PDF structures such as hidden or extremely small text.
Module C — Semantic Analysis: detects semantic anomalies and prompt-injection-style instructions.
Meta-Classifier: combines the three module signals.
Explainability: shows why a resume was flagged.
Adaptive Attacker: tests how easily the detector can be bypassed.
Existing Web Application: the current cinematic UI and live demonstrations remain.
3. Change #1 — Create One Common Detection Pipeline
Current issue
Different parts of the project currently perform the detection process slightly differently. For example, the web application and command-line path do not always handle model inputs in exactly the same way.
What we will do
Input Resume
     ↓
Clean / prepare input
     ↓
Module A
     ↓
Module B
     ↓
Module C
     ↓
Combine results
     ↓
Final decision
     ↓
Explanation
A single pipeline will be used by the web app, command-line tool, evaluation code, and tests.
Why
There should be one official way to analyze a resume. This removes inconsistencies and makes the system easier to maintain.
4. Change #2 — Fix Existing Bugs and Inconsistencies
Before adding new capabilities, all existing functionality must be made reliable.
Fix incorrect variable names and broken evaluation references.

Fix inconsistent thresholds and feature ordering.
Fix file path assumptions and import problems.
Remove duplicated inference logic and dead code.
Update comments and documentation that no longer match the implementation.
Regenerate stale results so the published numbers match the current code.
Target: everything that is already supposed to work should actually work.
5. Change #3 — Move Important Settings Into Configuration
Important settings such as detection thresholds, model paths, model names, random seeds, and limits should not be hidden inside source code.
configs/
├── model_config.json
├── thresholds.json
└── experiment_config.yaml
This gives the project one visible place for important settings and makes experiments easier to reproduce.
6. Change #4 — Make Module A Smarter
Module A currently relies heavily on exact keyword counting. We will keep the same purpose but make the detector better at recognizing real-world variations.
Normalize capitalization and punctuation.
Handle common aliases and abbreviations.
Recognize cases such as AWS vs. Amazon Web Services and K8s vs. Kubernetes.
Measure repeated keyword frequency, concentration, and unusual repetition patterns.
Use section-aware analysis where useful.
Keep the detector deterministic and independently testable.
The aim is to detect unnatural keyword stuffing, not simply count occurrences of the word "Python".
7. Change #5 — Make PDF Forensics More Real
Module B is an important part of the project, but some advertised PDF checks are currently limited or partially implemented. The upgrade should make the implementation match the claims.
Detect very small text.
Detect zero-size or suspicious bounding boxes.
Detect text placed outside the normal page area.
Detect invisible text where technically possible.
Investigate hidden PDF layers / Optional Content Groups where feasible.
Improve transparency and text-color analysis where the PDF format exposes enough information.
Use context when deciding whether white text is suspicious.
Important: white text by itself is not malicious. White text on a dark background can be legitimate; white text on a matching white background is more suspicious.
Real malicious PDF test fixtures should be created instead of relying only on synthetic text markers.
8. Change #6 — Make Module C More Meaningful
MiniLM can remain the semantic backbone if experiments continue to justify it.
Improve semantic coherence analysis.
Consider section-level consistency.
Use embedding-based anomaly signals where useful.
Keep prompt-injection detection as an explicit signal.
Separate normal semantic anomalies from direct instructions to an AI system.
This makes the output easier to explain: the system can distinguish between content that is semantically unusual and content that is actively trying to control the screener.

11. Change #9 — Test Different Types of Attacks Separately
Type A — Keyword stuffing
Type B — Hidden PDF text
Type C — Irrelevant technical jargon
Type D — Prompt injection and obfuscated attacks
Instead of publishing only one overall score, report performance for each attack type so the project's strengths and weaknesses are visible.
12. Change #10 — Make the Dataset Stronger
Keep the existing synthetic generation, but broaden the evaluation.
Synthetic attacks — generated automatically.
Human-designed attacks — realistic examples written manually.
Unseen attack styles — attack patterns not used to build the model.
Clean resumes — legitimate resumes with natural variation.
This reduces the risk that the model simply learns the patterns produced by its own attack generator.
13. Change #11 — Check for Data Leakage
Before trusting the metrics, check for exact duplicates, repeated templates, repeated attack payloads, and near-duplicate examples between development and test data.
The final report should only make a 'no leakage' claim after an actual automated check has been run.
14. Change #12 — Make the Train / Validation / Test Process Stricter

15. Change #13 — Choose the Final Detection Threshold Properly
A threshold of 0.5 is common, but it is not automatically the best choice for an adversarial detector.
0.10   0.20   0.30   0.40   0.50   0.60   0.70   0.80   0.90
Measure:
Precision
Recall
F1
False positives
False negatives
Select the final threshold deliberately based on the project's goals and the cost of missing an attack versus incorrectly flagging a clean resume.
16. Change #14 — Investigate Why the Model Misses Attacks
The existing model has better precision than recall. This means that many flagged attacks are correct, but the detector still misses a meaningful number of attacks.
Review false positives: clean resumes that were incorrectly flagged.
Review false negatives: attacks that were missed.
Identify which module failed for representative cases.
Document the likely reason for the failure.
Use the findings to guide improvements rather than simply chasing a higher score.
results/
  error_analysis/
    false_positives.md
    false_negatives.md
    representative_cases.json

34. What We Are NOT Planning To Do
No blockchain.
No unnecessary cloud infrastructure.
No microservices.
No Kubernetes.
No vector database unless a real requirement appears.
No random AI agents.
No unnecessary LLM APIs.
No completely new frontend.
No completely new ML architecture.
More technology does not automatically mean a better capstone. The goal is better evidence, not a longer list of tools.
35. Definition of the 10/10 Version
The system runs correctly.
CLI, API, and evaluation use the same inference logic.
The ML system is compared with meaningful baselines.
An ablation study proves what the modules contribute.
Attack types are evaluated separately.
The detector is tested against attempts to bypass it.
The dataset and split strategy are reproducible and leakage-checked.
The results can be reproduced.
The system explains why it flagged a resume.
Fairness analysis is responsible and accurately scoped.
The software has tests and CI.
The API has basic security hardening.
The documentation matches the implementation.
The existing cinematic demo remains polished.
